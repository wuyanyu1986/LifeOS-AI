# 技术架构方案

## 架构目标

- 先实现可运行的本地或半自动流程。
- 保证原始数据和结构化结果可追溯。
- 方便未来接入飞书、GitHub、数据库和前端应用。
- Agent Prompt 可版本化管理。

## 推荐技术栈

早期：

- Markdown 作为产品和 Prompt 文档载体。
- 本地脚本或轻量后端负责处理流程。
- 飞书文档作为知识库前端。
- GitHub 管理版本和 Issue。

后续：

- Node.js 或 Python 后端。
- SQLite 或 Postgres 存储结构化日记。
- 对象存储保存视频和音频文件。
- Web App 提供上传、查看、编辑和检索界面。
- 向量数据库支持语义检索。

## 数据流

```text
Media File
  -> Transcription Service
  -> Standard Parsed Note
  -> Feishu Sync
  -> Wiki Scanner
  -> Human Review Gate
  -> Parallel Content Generation
  -> Independent Output Reviews
  -> Memory Store
```

## 审核与通知

- MVP 每60秒扫描一次 `每日成长` 根节点的直接子文档。
- 使用 Wiki `node_token` 和内容修订号做去重。
- 标准解析稿审核通过前，视频脚本和公众号文章生成任务必须保持阻塞。
- 视频脚本和公众号文章生成后分别发送飞书消息，分别记录审核状态。
- 飞书文档读写继续使用 `siyangyuan-tiantu --as user`；消息发送与消息事件监听使用 bot 身份。
- 原生 Wiki 新建事件可用性确认前，不依赖事件推送；未来启用事件后仍保留定时扫描做一致性校验。

## 关键接口草案

### 创建日记

```http
POST /entries
```

### 获取日记

```http
GET /entries/{entry_id}
```

### 运行 Agent 流程

```http
POST /entries/{entry_id}/run
```

### 同步到飞书

```http
POST /entries/{entry_id}/sync/feishu
```

## 风险

- 视频和日记数据高度私密，需要默认本地优先或明确授权。
- Agent 输出可能过度推断，需要保留来源和置信度。
- 飞书 API 权限和文档结构需要稳定设计。
- 消息接收人、审核人身份和机器人所在会话需要显式配置。
- 扫描与消息发送必须具备幂等性，避免重复提醒和重复生成。
- 长期记忆可能积累错误，需要用户确认和可回滚机制。
