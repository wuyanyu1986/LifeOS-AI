# 跨系统架构与审核同步方案

**Version**: 0.1  
**Status**: Proposed

## 结论

飞书保留为个人知识库、长期内容展示、人工编辑、评论和审核入口。项目本地控制层负责内容版本、可比较快照、审核状态机、任务队列、重试和 Agent 调度。

飞书云文档有历史版本和编辑日志能力，但不能把界面里的历史版本直接当作稳定的程序化 diff 接口。因此版本比较采用“主动快照 + 本地 diff”作为主方案。飞书开放平台提供机器人、网页应用和事件订阅能力，可作为同步入口。citehttps://open.feishu.cn/community/articles/7355373610766761985

## 推荐分层

```text
飞书云文档 / Wiki
  内容展示、编辑、评论、人工审核
          ↕ API / 事件订阅
同步适配器
  拉取、规范化、hash、事件去重、写回状态
          ↕
LifeOS Control Plane
  SQLite/Postgres + 本地文件快照 + durable queue
  版本、diff、状态机、Agent 调度、通知重试
          ↕
Agent Runtime
  音频解析 / 记忆 / Viral Writer / 视觉生成
```

## 历史版本对比

每次生成或同步保存不可变快照，不依赖飞书 UI 历史版本列表：

```text
entries/<entry>/snapshots/
  parsed/current-content-r000.md
  parsed/current-content-r001.md
  parsed/audio-parse-unabridged-r000.md
  content/wechat-r000.md
  content/wechat-r001.md
  diffs/wechat-r000-r001.patch
```

每个快照登记 `snapshot_id`、`entry_id`、`stage/platform`、`source_revision`、`content_revision`、`feishu_doc_token`、`feishu_fetched_at`、`sha256` 和 `created_by`。

同步时从飞书读取文档，规范化为 Markdown，去除状态提示和展示噪声，再计算 SHA-256：相同则不产生版本；不同则保存新快照并生成 unified diff。飞书历史版本保留给人查看和恢复，项目快照作为 Agent 的差异分析、风格学习和回滚依据。

如果两次同步之间发生多次编辑，只能可靠知道同步前后状态，不能还原每一个中间状态。因此要保留短周期 reconciliation，并提供“本次修订完成”的显式动作；重要审核提交必须生成快照。

## 审核同步

消息只是通知，不是可靠状态源；“文档被修改”和“用户完成审核”也是两个不同事件。改为双通道：

### 快通道

部署 HTTPS 入口，订阅机器人消息、文档/评论相关事件和卡片回调。入口只负责验签、去重、写入 durable queue 并立即返回，不在回调中直接运行 Agent。飞书事件订阅的通用模式是平台向配置 URL 推送 HTTP 事件，事件处理与业务系统解耦。citehttps://open.feishu.cn/community/articles/7271149634339553282

### 慢通道

保留每 1-5 分钟的 reconciliation：拉取受管文档、比较 hash、补漏事件、修正状态、重试失败通知。事件负责低延迟，轮询负责最终一致性；两者写入同一个 durable queue。

## 审核交互

每条待审核消息提供“通过、要求修改、查看本次差异、查看无删减解析、重新生成当前分支”等按钮。按钮携带 `entry_id + stage + revision + action_id`，服务端校验 revision 仍为当前版本后再执行；旧按钮只返回版本已更新，不覆盖新内容。

飞书评论适合承载段落级意见，审核状态仍由本地控制层维护。评论事件可以作为补充触发，但不应直接充当状态机。

## 冲突处理

Agent 写回前必须校验 `expected_revision` 或 `expected_hash`：

```text
飞书仍为 r002 -> 允许 Agent 写回 r003
飞书已被用户改为 r002-user -> 保存双方快照，标记 conflict，等待选择合并策略
```

禁止 Agent 无条件全文覆盖飞书文档。

## 可扩展性判断

- 飞书作为内容和知识库：可行。
- 单人或小规模审核：事件订阅 + 本地控制层足够。
- 文本历史比较：本地快照比飞书历史版本更可控。
- 复杂状态机、长任务编排、重试和冲突合并：不应只依赖飞书。

未来从 SQLite 升级到 Postgres、从本地文件升级到对象存储时，飞书文档层无需重做。

## 实施顺序

1. 为每次生成/同步保存快照、hash 和 unified diff。
2. 增加 revision-aware 写回和冲突状态。
3. 将审核消息改成带按钮的卡片，按钮进入 durable queue。
4. 接入 HTTPS 事件入口，消息和评论走快通道。
5. 保留定时 reconciliation，监控事件延迟、丢失和重试率。
